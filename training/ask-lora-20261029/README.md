# Wisp Ask LoRA dataset (Gemma 4 E4B), 2026-10-29

This is a LoRA training set for Wisp's local Ask model. It targets the model-side failures found by the 1,040-question Ask eval run on 2026-10-29. Code-side failures were fixed in code (dev8, #410) and have no data here.

- **Built from:** `main` at `b8502786` (dev8 merged). `stats.json` records the head.
- **Size:** 920 examples: 833 train, 87 valid.
- **Status:** validated. No training run has been started.

## Files

| file | what |
| --- | --- |
| `train.jsonl`, `valid.jsonl` | mlx-lm chat-with-tools data |
| `train.meta.jsonl`, `valid.meta.jsonl` | metadata, line-aligned with the split files |
| `stats.json` | counts per family, split and target kind, plus the code head |
| `eval_questions.jsonl` | the 1,040 eval questions (prompts only), for the leak check |
| `brev/` | GPU training kit: renderer, Brev setup, trainer, merge and the oQ4e steps (see `brev/README.md`) |
| `builder/` | builder, validator and validator self-test |

`all.jsonl` and `meta.jsonl` (everything before the split) are regenerated by the build and git-ignored.

Each line is `{"messages": [system…, user, (assistant tool_calls, tool…)*, assistant], "tools": [...]}`.
- `tools` holds the exact schemas Wisp offered on that step. Usually that is about 6 full schemas, about 24 name-only stubs, and `get_tool_schemas`.
- Tool-call `arguments` are JSON **objects**, not strings. Gemma 4's chat template raises an error on the string form that the OpenAI wire format uses. Without this conversion, `mlx_lm.lora` would fail on the first example.

Each metadata line holds:
- `id`, `family`;
- `paraphrase_of`: the eval id whose wording this prompt replaced, else null;
- `notes`, `step`, `steps_in_turn`;
- `target_kind`: `call`, `load` (calling a stub to load its schema) or `final`;
- `prompt`, the frozen `clock`, `tool_choice` and `chat_template_kwargs`.

## How it was built

`builder/build.py` drives Wisp's real `POST /agent` handler in-process, through `fastapi.testclient.TestClient(app)` with no lifespan. A scripted "ideal model" plays each scenario. Every captured request becomes the input, and the scripted step is the target. So the system prompts, routing, head-start tools, stubs, schemas, hints and error re-prompts are exactly what this checkout's Wisp sends Gemma.

Safety of the build:
- `WISP_HOME` is a fresh temp dir, set before any `service` import.
- TCP and UDP are blocked in the process, so ports 8765, 8775, 8000 and the embedder are never contacted.
- No model loads, and no real tool runs.
- Every registry tool is replaced by a stub that answers from a synthetic world. Sam Rivera is a fictional CS student at the fictional Linden University. `get_upcoming`, `get_past_events` and `web_search` render through Wisp's own formatters.
- The clock is frozen per scenario, between Sep 2026 and Apr 2027, across every weekday, 7 AM to 11 PM.

A turn is kept only when all of these hold:
- the loop consumed the script exactly;
- no error event fired;
- the answer shown equals the scripted final;
- the host rewrote no argument;
- the prompt does not leak an eval question.

The build is deterministic: two runs give byte-identical files. It takes about 8 seconds.

Use the main checkout's `.venv` Python, which has fastapi, transformers and mlx-lm:

```bash
cd training/ask-lora-20261029/builder
PY=<main checkout>/.venv/bin/python
$PY build.py       # writes train/valid (+ all, meta, stats)
$PY validate.py    # exit 1 on any problem
$PY selftest.py    # proves the validator catches each problem
```

Optional deeper checks (both run clean on this build):

```bash
$PY validate.py --private-results <askeval>/results.jsonl \
    --template ~/Desktop/OMLX_Model_Files.hidden/Jundot/gemma-4-E4B-it-oQ4e-mtp
```

### What changed from the overnight build (853 examples at `2b5134e1`)

1. **Rebuilt at `b8502786`.** All 5,108 full schemas in the data equal the live registry's `Tool.schema()` byte for byte.
2. **Eval leak removed.** 297 of the 418 overnight turns asked an eval question word for word (311 counting near-copies).
   - All 269 distinct leaked prompts now use a same-meaning rewording, kept in `builder/paraphrases.json`.
   - `builder/leak.py` folds case, punctuation, weekdays, months and numbers. It then rejects a prompt that equals any eval question or has character-trigram Jaccard ≥ 0.7 to one.
   - The build drops a leaking turn, and the validator fails on one.
   - Four rewordings changed how the host routed the turn, so they were reworded again until the turn ran as scripted. Two more were corrected by hand for meaning.
3. **New family `ignore_embedded_instructions`** (31 turns): planted instructions in email bodies, notes, files, texts and web snippets. The six planted kinds are forward mail, text all contacts, reveal memory, delete reminders and events, set up a payment, and run a shell command.
4. **Held-out split by prompt group.** The overnight split was by turn, so the same question asked of two different worlds could land in both train and valid. The unit is now the folded prompt, and the validator checks the overlap is 0.
5. **Tool-call arguments as objects**, so Gemma's template renders them (see Files).
6. **Real tool errors in recovery examples.** The overnight set showed the stub's Python error ("World.t_summarize_emails() got…") in 27 examples. They now read exactly as the real tool's TypeError, and the validator fails on any trace of the harness.
7. **Stricter validator.** The privacy denylist now covers system prompts and tool schemas too (the overnight one exempted them). Added: live-registry checks, a reads-only rule, injection-payload checks, synthetic-only email domains, no `/Users/<account>` paths, the git identity and account name, the leak check, a template render, and a self-test.

## What `validate.py` checks

| check | rule |
| --- | --- |
| structure | legal role order; every history call has exactly one result |
| live tools | every offered schema equals what this checkout offers: full schemas exactly, name-only stubs, and `get_tool_schemas` (its families are a subset of the live ones) |
| calls | every call is to an offered tool that exists in the registry; target arguments validate against the schema (types, enums, required, no unknown arguments); `get_tool_schemas` names real tools |
| reads only | no call, in history or target, to a tool outside the read categories (`*_read`, `compute`, `wisp_admin`, `list_running_apps`) |
| injection | when a tool result has text addressed to an assistant, the target never repeats its payload (addresses, links, amounts, account numbers, commands) in a reply or an argument |
| privacy | email domains are synthetic (`linden.edu`, `example.*`, `fernbrooklabs.com`, `northlinebank.com`); no `/Users/<real account>`; no part of the git identity or macOS account name; with `--private-results`, no name, address, subject or title from the real eval results anywhere in the example. That denylist stays in memory only. |
| leak | the user prompt is not an eval question or a near-copy of one |
| markup | no `<\|tool_call>` text inside assistant content |
| split | no prompt group in both train and valid |
| template | (with `--template`) Gemma's chat template renders each example, and the prompt is a prefix of the full text, as `mask_prompt` needs |

`selftest.py` corrupts a real example in ten ways, one at a time. The validator reports each one.

## Known gaps

- **Thinking.** Production sends every step with `enable_thinking: true`. With that flag, Gemma's template forces a thought after each tool result. The examples here carry no reasoning; `brev/render.py` adds a one-sentence thought to those steps when it renders the training rows (see `brev/README.md`). Check reasoning-heavy questions after training.
- **Single turn only.** Follow-ups ("and tomorrow?") are not covered.
- **Emulated tool output.** Mail, messages, notes, activity, day plan, weather, Mac status and Wisp help copy the real formatters' shapes, but in simpler wording. Calendar and web use Wisp's own formatters.
- **Memory.** The fact store is empty, and memories come from the `recall` stub. The per-prompt memory block and the learned-routines card are absent.
- **Access mode.** The build runs in Full access, while the eval ran in View-only. No example writes, so no target changes.
- **Time zone.** The clock uses the build Mac's zone, America/Los_Angeles.
- **Host-misrouted questions are excluded** (code issues, not data): "do you know my birthday?" and "how much free disk space?" get no tools, and some "how do I…" web lookups have `web_search` forbidden. One injection web prompt was reworded to "search online for…" for that reason.
- **Code-side gaps from the eval are not covered:** no sent-mail tool, no folder sizes, the duplicate Gmail account, missing system fields. They are listed in the overnight report.
- **Paraphrases** were written to keep the meaning and every number, weekday and named entity. They were checked automatically and spot-read, not proven to need the same reply in every case.
- **Wisp's own prompt text** still includes a California-specific weather example and location module (`Palo Alto,CA`, from the initial snapshot) and the `Paris,TX` stand-in. These are public code, not user data. The private denylist treats them as reviewed public words.
- **The Brief redesign (#411)** was still open at build time. It changes UI, not Ask prompts. If it, or any later change, touches prompts or tools, rebuild before training.

## Training

Training runs on a rented GPU with Brev: see [`brev/README.md`](brev/README.md) for the recipe, its sources, the steps and what is still unverified. Nothing has been trained yet.

A local `mlx_lm.lora` run on this Mac was considered and dropped. It would have taken an estimated 4–10 hours with Wisp and oMLX quit. mlx-lm also renders prompts without `enable_thinking`, so it would train on prompts Wisp never sends.
