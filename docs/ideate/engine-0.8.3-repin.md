# Bundled engine re-pin: oMLX 0.8.2 to 0.8.3

Why: the user's standing rule is that the bundled engine follows the installed oMLX, and `/Applications/oMLX.app` is now 0.8.3 (Team ID PSK5Q5T46L). Everything below was computed read-only from `/Applications/oMLX.app`. The engine was never started, no model was loaded, nothing was downloaded, and no GPU work ran.

This is a risk-triggered change (native integration, memory guard, release pins). It needs an independent Release Auditor verdict on the exact candidate SHA before any release. A preview build may use it before that.

## How the 0.8.2 baseline was recovered

No 0.8.2 oMLX.app is installed, but `/Applications/Harbor.app` (build 69, on 0.8.2) holds the overlaid 0.8.2 engine. Applying the Wisp to Harbor rename in reverse (`harbor_*` to `wisp_*`, `Harbor` to `Wisp`) reproduced each patch's pinned `output_sha256` exactly. Reversing each guard edit then rebuilt all eight 0.8.2 inputs, and each matched its pinned `input_sha256` exactly. Every 0.8.3 change near an edit was read as a real diff against that baseline. (No 0.8.2 DMG or tree was found cached under the repo's `.harbor-build` folders, and none was needed.)

## Per patch

- `omlx/__init__.py`, `omlx/patches/gemma4_verify_attention.py`, `omlx/patches/gemma4_verify_kernel.py`: byte-identical upstream. No change.
- `omlx/engine/vlm.py` (3 edits, encoders on demand): all edits apply unchanged, so only the checksums move. 0.8.3 adds `_apply_inkling2_reasoning_mode` (maps thinking switches to Inkling 2's `reasoning_effort`), a Hy4 Engram SSD loader branch, and an `engram.close()` in `stop()`. The encoder attach still runs after `_inject_tool_calling` and just before `_loaded = True`, and detach still runs first in `stop()`. mlx-vlm is still 0.7.11 with a byte-identical gemma4 package and `utils.py`, so `wisp_encoders` is unaffected.
- `omlx/engine_pool.py` (24 edits, admission and owned unload): all 24 apply unchanged at the same counts. 0.8.3 adds Hy4 Engram SSD offload (a lower resident-size estimate for `hy_v4_flash` models only when that per-model setting is on, a VLM-engine requirement, and a re-raise instead of the force-LM fallback when the start fails). The `GuardEvidenceUnavailable` re-raise still comes first in the start failure handler, and `entry._wisp_active_engine = engine` plus `bind_start` still sit right after the Splash registration, before the early prefill helper, as ported in 0.8.2. `_start_engine`, `_unload_engine` and `_stop_and_unload_engine` are unchanged upstream.
- `omlx/patches/mlx_lm_mtp/batch_generator.py` (4 edits, MTP failure falls back): all edits apply unchanged. 0.8.3 only changes the context-copy proposal (16-row wide windows for Inkling 2, a longer copy is no longer clipped to the drafter block). It does not touch the code paths the edits wrap.
- `omlx/process_memory_enforcer.py` (12 edits, evidence and sampling hooks): all edits apply unchanged. 0.8.3 adds `get_graphics_footprint_compressed()` to `_cpu_footprint_bytes()` (compressed Metal pages leave the graphics ledger but stay in the physical footprint). That lowers the CPU footprint term, so the Metal-cap term of the hard limit gets slightly lower, never higher. It sits in a helper that none of the edits wrap, and `_propagate_memory_limit` (the branch the propagation fixture pins) is unchanged.
- `omlx/server.py` (14 edits, guard wiring, `start_bound` for 3 `engine.start()` sites, encoder routes): all edits apply unchanged at the same counts. (A raw-input anchor check flags edit 13 only because its anchor, the `wisp_guard` import, is added by edit 1; applied in order it matches once.) 0.8.3 adds one new import and an early return in the Anthropic `/v1/messages` handler: `maybe_handle_anthropic_web_search` answers a request that carries a `web_search_*` tool by running the configured web search provider, before any engine lookup. It starts no model.
- Start sites: the patched `server.py`, `engine_pool.py` and `engine/vlm.py` list exactly the same `.start(`, `_start_engine(`, `_load_engine(`, `start_bound` and `bind_start` sites as the shipped 0.8.2 files. Across the rest of `omlx/` the site list is identical between versions. No new call site starts an engine outside the pool or server paths the guard already wraps.
- Additions (`wisp_guard`, `wisp_encoders`, `wisp_kernel_guard`): unchanged. Every private upstream attribute they read (`_unloading_models`, `_stop_and_unload_engine`, `_entries`, `_memory_guard_tier`, `_prefill_memory_guard`, `_current_poll_interval`, `_running`, `_task`, `_propagate_memory_limit`, `_loaded`, `_vlm_model`, `_model_name`, `_engine`, `_mlx_executor`, and `omlx.exceptions.OMLXError`) still exists in 0.8.3, and no upstream `omlx/wisp_*` file collides.

No edit was dropped, no edit needed porting, and no guard was weakened. A full overlay `apply` of the manifest onto a copy of the eight 0.8.3 files verified all 11 outputs.

## Pins

- `engine.lock.json`: 0.8.3, tree `b9ce3915...faca`, minimum macOS 26.2, from `engine.py lock --app /Applications/oMLX.app`. The codesign Team ID check passed.
- `engine_guard/manifest.json`: `upstream_tree_sha256` equals the lock. The patch, input, output and patch-file hashes of the five changed patches (vlm, engine_pool, batch_generator, process_memory_enforcer, server) were recomputed, and the three byte-identical rows are unchanged. The patch files' own `input_sha256` and `output_sha256` fields moved with them.
- `tests/fixtures/engine_guard/propagation_branch.json`: input and output hashes follow the `process_memory_enforcer.py` row. The branch source and its AST hash are unchanged (the branch is byte-for-byte the same AST in the patched 0.8.3 file).
- `engine-source.json`: **UNVERIFIED.** Tag `v0.8.3`, version `0.8.3`, asset `oMLX-0.8.3-macos26-27.dmg` (assumed from the 0.7.3 naming). `size` and `sha256` are placeholders (1 and all zeros) with an `unverified` note, as for 0.8.2. A `--fetch-engine` or CI download fails closed on the size check until someone sets these three fields from GitHub's v0.8.3 release asset. Local `--engine-app /Applications/oMLX.app` builds are unaffected.
- `tests/test_engine_packaging.py`: the asset URL expectation is now `v0.8.3/oMLX-0.8.3-macos26-27.dmg`. No other test or build-support file pins the bundled engine version.
- `engine-prune.json`: unchanged. Every dropped name still matches a top-level entry in 0.8.3 except `phonemizer_fork`, which is a dist-info name (its package directory is `phonemizer`, which is dropped). New and removed top-level packages versus the shipped 0.8.2: none. Only two kept dependencies changed version (`decorator` 5.3.1 to 5.3.2, `filelock` 4.2.12 to 4.3.0). The prune list must still be re-validated by `scripts/engine_smoke.py` (it starts the engine, so it was not run here).
- `engine-licenses.json`: unchanged. The repo's licence gate over the selected 0.8.3 tree (139 packages) reports no problems. The non-permissive set is the same as before (certifi, mlx-embeddings, pycountry, soxr, tqdm, zeroconf, all already reviewed). 0.8.3 ships no top-level oMLX licence file to compare `engine-licenses/oMLX-LICENSE.txt` against.

## Risks for the Auditor

- The DMG size and SHA-256 are unverified, so a release CI fetch cannot pass until they are filled.
- 0.8.3 adds a web search answer path on `/v1/messages` (only when a request carries a `web_search_*` tool, using whatever provider the engine's integration settings name). It runs before engine lookup and starts no model, but it is a new outbound-network route inside the engine. Wisp's own client does not send that tool. Worth confirming the bundled engine's default integration settings leave the provider empty.
- Hy4 Engram SSD offload lowers the admission size for `hy_v4_flash` models when its per-model setting is on. It is off by default and Wisp does not run Hy4, but the guard trusts upstream's estimate there.
- The `_cpu_footprint_bytes` change makes the Metal-cap term slightly lower, not higher, so it is the safer direction for admission; the guard's evidence hooks do not wrap it.
- The engine smoke run and the real-GPU kernel test (`test_real_kernels_on_this_gpu_with_a_448_thread_cap`) were not run: no engine or GPU work was allowed in this task.
