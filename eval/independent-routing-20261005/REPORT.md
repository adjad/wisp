# Wisp routing evaluation — October 5, 2026

**Recommendation: use Ling to interpret flexible requests into a typed intent, with deterministic code compiling and validating the actual calls. Keep a small set of proven exact fast paths. Do not give Ling unrestricted responsibility for every routing decision, and do not add either tested Laya checkpoint to the default routing path yet.**

The best measured model-assisted prototype was the revised Ling intent compiler. It got 28 of 36 fresh held-out requests completely right under the original strict rubric, compared with 8 for the frozen current rules, 11 for direct Ling tool selection, and 19 for the original Ling intent prototype. It still failed eight requests, so this is an architectural recommendation, not a production-readiness verdict. The fast-path-plus-revised-intent combination is a proposed integration; that combined production path was not measured end to end.

The week failure and the unpleasant overview presentation have separate causes. Changing the routing model alone will not address both.

**What was actually tested.** All model inference ran locally on this Mac (`Mac17,8`, 24 GiB unified memory). Ling was the resident `Ling-3.0-tiny-oQ6e`. No native, personal-data, or outbound tool was executed; proposed calls were scored as data. Follow-on answers used synthetic source fixtures. Production settings, live model residency and Claude's implementation were left untouched.

There were 2,916 held-out routing trials across two held-out sets containing 174 distinct requests, plus 120 ambiguity/capability trials, 1,008 Laya source/order checks (including development and challenge cases) and 165 synthetic answer continuations. Development sets were separate. Repetitions and paraphrases are correlated, not thousands of independent user samples. The original benchmark was frozen before primary held-out inference. After it exposed context-format problems, a separate author created a fresh corpus; the revised candidate was developed only on its development split, reviewed and frozen before its 36 test cases were read or run. No candidate was tuned on that fresh test output.

**Original comparison: 138 held-out requests, three repetitions per candidate.** Strict success requires the expected first tool calls and checked arguments, with no extra/excluded effects. All repetitions agreed on pass/fail, so the fractions below use distinct requests. The baseline runs frozen production routing/read shortcuts followed, where needed, by controlled Ling generation. Direct Ling sees a compact 25-tool catalog, not Wisp's entire registry.

Choosing the source is insufficient: direct Ling usually chose the right source but frequently produced the wrong date range, operation or filters. A named calendar week must use its exact boundaries; `days=7` is a rolling horizon. The original typed-intent path's family-balanced gain over rules was 11.3 percentage points, with a descriptive family bootstrap interval of 1.0–22.8 points. This characterizes this authored corpus, not future user-population accuracy.

The original conversation fixtures included synthetic `[Tools: ...]` annotations in assistant prose. Some planner outputs became arrays or malformed JSON, and some continuations copied only a tool marker. That is a material fidelity limitation. A six-request development diagnostic varied context encoding and JSON format: the annotated `json_object` condition returned objects in 10/12 trials; the strict-schema and marker-free role-history conditions did so in 12/12. Semantic errors remained. The revised test below uses natural conversation text plus separate prior-tool metadata, equally available to rules and model paths. Its gains cannot be attributed to any one prompt/schema change in isolation.

**Fresh comparison: 36 different held-out requests, three repetitions each.** These are a smaller, deliberately difficult set; do not compare their percentages directly with the original table. The revised path uses a typed JSON schema, local validation, deterministic date/read compilation, one repair for invalid output, and no tool fallback for inline/no-action intent. It does not execute actions.

The revised path passed all fresh personal-week, month, exact-agenda-range and context-correction cases. Its remaining failures are concrete: unread state embedded in a text query instead of a Boolean filter; a conversation recap treated as unfiltered records; a contact name changed from `Imani` to `Youmani`; a stale public-location filter carried into a personal agenda; one missing source in a combined email/text request; and a literal recipient changed by dropping its leading `+`. These failures were preserved, not repaired against the test set. One distinct request needed the bounded repair; there were no transport/parse errors or extra-effect proposals in this fresh run. That does not establish general action safety.

**Scoring sensitivity.** Original strict scores are retained for reproducibility. An independent sensitivity audit, reproduced in `scoring_sensitivity.json`, accepted provably equivalent omitted defaults, harmless explicit defaults, and removed one over-specified `calendar_only` requirement. It changed **zero** case or trial outcomes in either corpus or the English replication; the table rankings are unchanged. Strict first-call scores can penalize equivalent argument representations and can also miss semantic errors in permissive substring query checks. They are not end-to-end successful-answer rates. Sender queries must match the actual local search implementation; unsupported search syntax such as `from:Acme is:unread` is not made valid merely because the string contains `Acme`.

Multilingual Laya fell back on 48.6% of hybrid trials; English Laya on 37.0%. Neither hybrid beat the original rules on strict accuracy. The English checkpoint's runtime warns that its 11+ option temperature is clamped and the affected probability bucket is uncalibrated. Reversing its options changed source accuracy to 94/138, another reason not to treat a high probability as dependable authority. No source/order run had input truncation or collapsed options.

The models are distinct: multilingual `aac6fef/laya-multilingual-coreml@8139e9089273319512c730218903784074133187` used `laya-coreml==0.2.0`, CPU/GPU FP16; English `aac6fef/laya-mlx` matched publication revision `047678560251f28113ee8f5df4be82102c7bf336` and used `laya-mlx==0.3.0`, GPU FP16. English checkpoint files were verified before and after the scored runs; the multilingual checkpoint files were hash-verified after measurement. The English agent has a 512-token input budget; the multilingual agent has 1024. Local weights, configs and tokenizers were verified. The [English runtime](https://github.com/mizorewww/laya-mlx/blob/v0.3.0/README.md) and [calibration implementation](https://github.com/mizorewww/laya-mlx/blob/v0.3.0/laya_mlx/common.py) describe the different runtime and temperature behavior. These results should not be generalized to every Laya/System 1 model or a separately trained router.

Jev remains **unmeasured**: no pre-existing authorized configured credential was available. Its [official API documentation](https://api.typesafe.ai/redoc) makes it a possible later contender; there is no measured basis here to rank its accuracy, latency or cost against the local candidates.

**Latency and memory limits.** Table timings are routing-stage wall time, excluding real source access and final answer delivery. Ling stayed resident throughout; a cold Ling model start was deliberately not measured. Cache conditions differed: all original direct-Ling generation calls had cached prefixes, whereas most intent calls did not. English Laya ran later, so its timing comparison is sequential rather than an interleaved checkpoint experiment. CoreML model-load readiness was 4.42 seconds in the primary run; English readiness was 0.106 seconds in its scored run, with a largest observed source pass of 0.607 seconds. Readiness excludes imports and can exclude lazy device work; neither number is a standardized cold-start comparison. Process RSS is not complete GPU/unified-memory usage. Ling's server reported about 6.69 GB actual model size; these quantities should not be added as a precise total. Desktop-wide exclusivity was not guaranteed. All inference was serialized and memory-guarded.

**Why the reported weekly wording failed.** At frozen base `fa66cb3`, the implicit personal-agenda grammar misses expanded “what is up for this week.” The web parser removes the date/question words, leaves `up`, labels the remaining subject external, and constructs a public query. The router dispatches that query before normal calendar continuation. The read shortcut also requires a calendar/schedule noun. This is a rule-ordering and grammar defect. A separate post-freeze regression replay of the exact wording with synthetic calendar context produced `get_upcoming(period="this week")` on all three revised-intent runs. This known-example check is recorded in `reported_week_regression.json`; it is not counted as fresh held-out evidence and did not trigger further tuning. Source anchors: `service/router/web_request.py:753`, `:922`, `:996`; `service/router/router.py:7134`; `service/workflows/reads.py:312`.

**Overview presentation needs its own repair.** Frozen production already groups calendar items by day and separates reminders; email summaries use a deterministic sender digest; message summaries use conversation grouping with validated topic labels. Successful single summary calls often bypass extra model narration. The problem is not simply a lack of prose generation. Dense counts/coverage footers, repeated subjects, wrong selection of raw-record tools for a summary, and multi-source merging can make the result unpleasant. The merge helper retains only the first result per tool name, so source/scope-aware merging deserves review. Source anchors: `service/tools/assistant_tools.py:248`; `service/tools/email_tools.py:1186`, `:1407`; `service/tools/message_digest.py:490`; `service/agent/loop.py:1082`, `:1852`, `:2888`.

The 165 controlled answer continuations were audited blind by three independent helpers using a shared rubric. Reviewers found 23 answers with fabricated counts or unsupported absence/completeness claims, nine marker-only nonanswers, and recurring incoming/outgoing attribution errors. Only 4 of 55 partial-source answers received full marks across all five dimensions. Quoted note instructions were not followed; optional offers to help were not counted as unauthorized actions. Overall, 54/165 continuations received full marks. Among the 51 continuations whose first calls were correct, 19/51 received full marks and 2/51 still had critical failures: correct routing does not ensure a grounded answer. No repeated read or unfinished tool call occurred in this bounded synthetic continuation harness. These results do not validate the production UI, native sync, production digest short-circuits or recovery from the original repeated web searches. Each answer had one reviewer; this is an exploratory quality audit, not a human preference study.

**The routing path to implement and validate next:**

1. Keep a small exact-read/command fast path with explicit source and date bindings. Fix the shared personal-agenda grammar and context precedence; do not infer “public web” merely from a time phrase and an otherwise unrecognized word.
2. Route flexible phrasing and context corrections through Ling's typed intent. Locally validate the object, compile supported reads, and allow one bounded repair. Invalid or ambiguous plans need clarification or a precise limitation, not an unbounded new tool search.
3. Enforce source exclusions, explicit action authorization, exact date boundaries and required filters in deterministic code. Preserve literal entities/recipients, represent unread as a typed field, drop stale filters on source changes, and verify every requested source is present. A model's confidence is never permission.
4. After the scoped tool step, carry source, direction, scope, coverage and receipts as structured evidence. Reuse unchanged read results; retry only when source/query/scope or coverage changes. Do not equate permission-denied with empty.
5. Render one compact overview: agenda by day; messages by conversation with “you” versus correspondent explicit; one brief coverage limitation when it changes the answer. Keep authoritative dates/counts and existing validated digest machinery. Avoid an extra unconstrained rewrite of an already complete digest.

For the complete synthetic weekly fixture, a target layout is simply: “Oct 5–11 — two events and one reminder,” followed by Monday 9 AM planning, Tuesday 4 PM call-dentist reminder, and Friday noon lunch. In the partial fixture, omit the unavailable Work-calendar lunch and say “Work calendar could not be checked.” This illustrates the intended presentation, not a screenshot or a measured UI redesign.
